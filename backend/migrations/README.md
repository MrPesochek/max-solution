# Миграции схемы

Alembic, линейная цепочка `versions/0001…`, SQL пишется руками (`op.execute`), автогенерация
не используется. Новая ревизия: скопировать последний файл, поднять номер, заполнить
`revision`/`down_revision`, описать изменение в первой строке docstring — она попадает в
`alembic history` и в список миграций, который печатает `scripts/deploy.sh` перед выкладкой.

## Как миграции применяются на стенде

- Сервис `migrate` (compose) выполняет `python -m app.db.migrate`: `alembic upgrade head`, но
  если голова кода уже есть в журнале `schema_revisions`, миграции не запускаются и команда
  завершается успешно — так прежний образ стартует на БД, поднятой более новой версией.
- Журнал `schema_revisions` ведёт хук `on_version_apply` в `env.py`
  (`app.db.schema_revisions.record_step`): строка добавляется при `upgrade` и удаляется при
  `downgrade`. Таблицу создала миграция 0024 и заполнила задним числом всей цепочкой до себя.
  `alembic stamp` и offline-режим (`--sql`) журнал не ведут.
- Readiness `api` (`/readyz`) требует, чтобы голова кода была в журнале: схема на голове кода
  или новее — ok; журнала нет или головы кода в нём нет — 503 (`схема БД старше кода,
  выполните миграции`).
- Откат образов (`scripts/deploy.sh --rollback`, автооткат) схему не понижает: старый код
  работает на новой схеме. `alembic downgrade` в бою не выполняется.

## Политика: expand / contract

Откат образов возможен только если каждая миграция обратно совместима с предыдущей версией
кода. Поэтому одна выкладка только расширяет схему:

| Можно в любой выкладке (expand) | Только отдельным релизом позже (contract) |
|---|---|
| новая таблица | удаление таблицы или столбца |
| новый столбец `NULL` или с `DEFAULT` | переименование таблицы или столбца |
| новый индекс (в т.ч. частичный) | `NOT NULL` без `DEFAULT` на существующем столбце |
| ослабление ограничения (`CHECK` шире, `DROP NOT NULL`) | смена типа столбца |
| данные-справочники (`INSERT … ON CONFLICT DO NOTHING`) | новые `UNIQUE`/`CHECK`, которые отвергнут записи старого кода |
| | удаление индекса, на который опирается запрос старого кода |
| | массовое изменение данных, которое старый код трактует иначе |

Порядок при удалении и переименовании: релиз N добавляет новое и учит код писать в оба
места (или читать старое как запасное), релиз N+1 — когда откат на N−1 уже не нужен —
убирает старое. Новое значение перечисления (статус, тип) — тоже расширение, но старый код
может его не знать: убедитесь, что он такие строки не роняет, иначе это contract.

## Миграции, ломающие откат

Если без нарушения политики не обойтись (или миграция меняет данные так, что предыдущая
версия будет работать неправильно), пометьте это в **первой строке docstring** ревизии
суффиксом `[ломает откат]` и назовите в теле причину и минимальную совместимую версию:

```python
"""переименование requests.note -> comment [ломает откат]

Совместимость: код до тега 20261001120000-abcdef123456 с этой схемой не работает;
откат — только восстановлением БД из дампа перед выкладкой.
...
```

`scripts/deploy.sh` видит пометку в списке миграций и печатает предупреждение: после такой
выкладки путь назад — `scripts/restore.sh` из дампа, сделанного перед миграциями, а не
`--rollback`. В остальных случаях в комментарии к `upgrade()` достаточно строки о том, почему
изменение обратно совместимо (как в 0020–0022).
